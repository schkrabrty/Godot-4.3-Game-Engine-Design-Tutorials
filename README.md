# Godot-4.3-Game-Engine-Design-Tutorials

In this tutorial, I will show you five examples of `Custom Physics Constraint`, `Custom Collision Response Handler`, `Surface-Dependent Friction & Bounciness`, `Wind and Aerodynamics Simulation`, and `Custom Gravity Fields`. Let's start to discuss about them in the following sections.

## Custom Physics Constraint
In this example, we will develop a custom C++ node where we can simulate **magnetic attraction** and **repulsion**. You can open the `custom_physics_constraint.tscn` scene to see a tutorial of this example. In the `src` folder of this project, you can find the `magnetic_constraint.cpp` file, where the main logic is written. The overall idea is that, this node (or the `MagneticConstraint` node) will consider two `RigidBody2D`s. Now, based on the distance between two of them, they will either be magnetically attracted or repelled. I played with the value of the magnetic force to make the visual attraction or repulsion effect more pleasing and realistic. I found that the magnetic force of `100000000.0` pixels/second<sup>2</sup> can give a better visual effect of the force. In this example, the maximum distance between the two rigid bodies is set to `500` pixels. This means if the distance between the rigid bodies become lesser than 500 pixels they can attract or repel themselves with the force mentioned earlier. There is also another variable called `polarity` which detects whether the magnetic force is attractive or repulsive. If the `polarity` is `1`, the force is attractive, and if it is `-1`, the force is repulsive. The polarity of the magnetic force can be dynamically changed by pressing the `Space Bar` while running the game. I also attached a GDscript to both rigid bodies in Godot. The name of that script is `Player_RigidBody_2D.gd`. Using this script, you can move the rigid bodies with keyboard inputs. The left rigid body can be moved by `W`, `A`, `S`, and `D` keys, and the right rigid body can be moved using the `Up`, `Down`, `Left`, and `Right` arrow keys. I created some `Input Actions` in Godot to represent those keys. In that script, I created a `bool` variable called `isLeft`. This variable is set to `true` if the corresponding rigid body locates on the left side of the screen at the beginning of the game. The value of this variable is false for the other rigid body. Because the script is attached to rigid bodies, we need to apply force to move them. By default, I considered the `Move Force` to be `100` pixels/second<sup>2</sup>. However, you can definitely play with the value. After you play the game, you can press the `WASD` keys or the `Arrow` keys to move both rigid bodies. By default, the `polarity` of the magnetic force is set to `1`, i.e., the rigid bodies will attract themselves. So, you can move the rigid bodies closer to each other. When the distance between them becomes lesser than `500` pixels, you will be able to see the effect of the attractive magnetic force between the rigid bodies. If you want to repel them after they are stuck together, you can press the `Space Bar`, and you will be able to see the effect of the repelling force. Finally, I turned off the gravity of both rigid bodies in this example (or changed the `Gravity Scale` value to 0 under the `RigidBody2D` section in the `Inspector` window) so that they will not fall down automatically.

Even though the assignment asks you to use `Jolt Physics Engine`, you can still work with 2D physics, as the basic idea remains the same. However, if you want a similar example in 3D, you can find it in a separate scene called `custom_physics_constraint_3D.tscn` in Godot. The corresponding C++ script can be found in the `src` folder, which is called `magnetic_constraint_3d.cpp`. The only changes that I did in this new C++ script is, I changed all the `2D`s to `3D`s, and that's it. The Godot project needed a little more changes to make it work in 3D. So, instead of `RigidBody2D`, I used `RigidBody3D`. Instead of `Sprite2D`, I used `MeshInstance3D` to create a 3D cube. I also added a `Camera3D` node because without a camera, we cannot see the 3D virtual world. Finally, I wrote a separate GDScript called `player_RIgidBody_3D.gd`, which is very similar to the other GDScript mentioned before. This script will allow you to move the rigid bodies based on your key inputs. I turned off the gravity of the rigid bodies in this example as well. The `Max Distance` between the rigid bodies is set to `5` meters in this case. The magnetic force is set to `100` pixels/second<sup>2</sup>. The `Move Force` of the rigid bodies by the key press events is set to `10` pixels/second<sup>2</sup> in this example.

**NOTE: (i) To download the `Jolt Physics Engine`, you can go to [this link](https://godotengine.org/asset-library/asset/1918) first, and download the zip file to your computer. Next, unzip it. Once it is finished, Godot will automatically restart, or it will ask you to restart it, or you need to manually restart it to install the addon properly. **(ii) The main magnetic attraction and repulsion forces are calculated using the *Inverse Square Law* shown in the Assignment, i.e., `dir.normalized() * (magnetic_force / (distance * distance)` where `dir` means the direction between two nodes and `distance` represents the actual distance between the two nodes.**

## Custom Collision Response Handler
In this example, we will see if two rigid bodies collide with each other then based on their impact velocities, there can be cracks on them. You can find this example in the `custom_collision_response_handler.tscn` scene. In that scene, the `Player` and the `Enemy` nodes are the customized C++ node, which mainly extend from `RigidBody2D`. The customized C++ script that is attached to these nodes is called ad `collision_response_controller.cpp` in the `src` folder. The main idea of this script is to detect what is the velocity of both nodes during collision, and calculating the resultant impact velocity (which is the difference between these two velocities). If it is more than `200` meter/second (which we defined as the default value of the `Impact Threshold` variable), then the crack will show up on the node. However, if the impact velocity is lesser than that value, then no crack will show up on the node. For simulating cracks, I created some pictures in PhotoShop and place them in the `classDemo -> Images -> Deformed Images` and then `Enemy` or `Player` folders. The idea is, whenever there is a collision greater than the threshold value, each of the cracks will show up on the respective nodes. However, when all the five images are shown on the nodes, they will be destroyed on the next collision greater than the `impact Threshold` value. Now, while determining the collision, there is a high chance that if two objects collide with each other very hard, there can be multiple trailing collisions between them because of bounciness. In that case, the subsequent bouncing impacts can also be greater than the `Impact Threshold` value. So, basically, there can be a chance that all the crack textures can be quickly rendered on the node subsequently because of the subsequent collisions one after the other. As a result, you may not be able to see all the five textures individually (as they can render very fast subsequently). To get rid of this problem, we can implement a cool down timer in our C++ script which will start the timer for some time when a big collision (greater than the `Impact Threshold` value) occurs between the rigid bodies. When the cool down timer expires, then we can again check if there is any other major collision occurring between the rigid bodies. 

I also, added the same `Player_RigidBody_2D.gd` GDScript mentioned earlier with the `Player` and the `Enemy` custom C++ nodes to move the rigid bodies in the game with key board inputs. Feel free to test the game to understand the example properly. Also, you can theoretically change the shape of the collision shape of the rigid bodies after each collision. This means, you can create dents in the collision shapes. For doing that, you need to use `CollisionPolygon2D` instead of `CollisionShape2D` because `CollisionPolygon2D` allows you to create your customized collision shape that is created by stitching lots of points whereas `CollisionShape2D` has very fewer points to work with and it is mainly used for collision detection. Once you have lots of points in the `CollisionPolygon2D` shape, you can theoretically manipulate the shape after each major collision. I tried to write a code in the C++ script for that, but I never made it work properly. So, I left the code as it is for your understanding, but the function (i.e., `simulate_dent()`) is never called in the script. 

**NOTE: Whenever you want to access the impact velocity and other collision related physics variables, you need to access the current physics state of the game. You can access that state by calling the `_integrate_forces()` method and passing the `PhysicsDirectBodyState2D *state` variable as a parameter with the function. This method is automatically called in each `_physics_process()` call. So, you do not need to call the `_integrate_forces()` method explicitly from anywhere in your code. However, in order to make it call properly from the C++ script, make sure to include these two lines of codes below, in your `_ready()` method in your C++ file. They are -**

**`set_contact_monitor(true);` and** 

**`set_max_contacts_reported(10);` where 10 means the maximum number of collision contact points that you want to pass to your `_integrate_forces()` method.** 

**If you forget to include these lines in your C++ script, the `_integrate_forces()` method will not detect contact points during the collisions, and as a result no code in this method would execute further. So, make sure to include those two lines of codes in the `_ready()` method of your C++ script.** 

## Surface-Dependent Friction & Bounciness
In this example, we will play with the `Physics Material` of Godot. By changing the `Friction`, `Bounce`, `Rough`, and `Absorbent` properties of this material, we can make the surface of a rigid body more slippery or rough or bouncy or absorbent. You can open the `surface_dependent_friction.tscn` scene in Godot to see this example. Over there, I created a `CustomPlatform` C++ node which is located at the bottom of the screen. There is also a `Player` node which is basically a normal `RigidBody2D` node. I attached the `Player_RigidBody_2D.gd` GDScript (mentioned earlier) with the `Player` node so that we can move it with key board input events. I have also created a small UI element to expose the `Friction`, `Bounce`, `Rough`, and `Absorbent` properties of the `Physics Material` to the game. The main idea of this example is, we can play with the UI element to change the properties of the `Physics Material` assigned to the `CustomPlatform` C++ node. Based on the surface property of this node, the `Player` rigid body can move accordingly. This means, if the surface is slippery, the `Player` node will move very quickly with less bounce. However, if the surface is very rough, then it will have hard time to move and because of friction, it can start to bounce a lot. If the surface is absorbent, then it will be harder for us to move the `Player`. 

The `CustomPlatform` extended from a `StaticBody2D`. We can definitely make it as a `RigidBody2D` node. However, my intention was to make this node static (like a wall or ground). So, instead of a `RigidBody2D`, I used a `StaticBody2D` node. Now, through the C++ code, I created and assigned a `Physics material` to the `Physics Material Override` property of the `StaticBody2D` node. Next, I simply played with the parameter values of the assigned `Physics Material` to the `StaticBody2D` node. 

**NOTE: The `Physics Material` can only be assigned to either `RigidBody2D` nodes or `StaticBody2D` nodes. The other nodes for collision detection such as `CharacterBody2D` nodes or `Area2D` nodes will not work with `Physics Material`. So, if you want to change the properties of the `Physics Material`, make sure that you are working with either `RigidBody2D` nodes or `StaticBody2D` nodes.**

## Wind and Aerodynamics Simulation
In this example, we will play with the wind simulation. You can find this example in the `wind-and_aerodynamics_simulation.tscn` scene in Godot. There are two `RigidBody2D` nodes, an `Air Baloon` and a `Flying Debris`. The `Mass` of the `Air Baloon` and the `Flying Debris` nodes are set to `0.04` Kg, and `0.3` Kg respectively to simulate weight in them. I also attached the `Player_RigidBody_2D.gd` GDScript with both rigid bodies so that they can be moved using Key board inputs. The `Move Force` of the `Air Baloon` and the `Flying Debris` nodes are set to `10` pixels/second<sup>2</sup> and `50` pixels/second<sup>2</sup>, to simulate slight and medium forces on these nodes respectively. The wind field is simulated by creating a custom C++ node called `WindArea2D`. The corresponding C++ script, i.e., `wind_2d.cpp` can be found in the `src` folder of this project. This node is extended from an `Area2D` node. We can span this `Area2D` node in the entire scene space (which I have done in this example) or you can span it at some localized area based on your game's need. There is an UI element which exposes the crucial parameters of the `WindArea2D` C++ node, i.e., `Wind Speed`, `Wind Direction`, `Gust Intensity`, `Gust Frequency`, and `Air Density`. When you play the game, you can dynamically change the value of these parameters and based on that you can see the movement of the `Air Baloon` and the `Flying Debris` will be changed. There is also a red directional arrow placed in the middle of the scene throughout the runtime of the game to represent the direction of the wind in the game. As the weight of the `Flying Debris` is greater than the weight of the `Air Baloon`, it will fall down to the ground quicker than the `Air Baloon`. 

**NOTE: The main equation that we need to implement in this example is the *Drag Force Equation* which is -**

**F<sub>d</sub> = <sup>1</sup>&frasl;<sub>2</sub>&rho;v<sup>2</sup>C<sub>d</sub>A**

**where:**

**- F<sub>d</sub> is the drag force imposed by the air,**

**- &rho; is the air density,**

**- v is the velocity of the object relative to the air,**

**- C<sub>d</sub> is the drag coefficient, and**

**- A is the reference area.**

**(C<sub>d</sub> * A) is a constant. In this example, we considered the value of this constant to be `0.1`. The value of &rho; is `1.225` kg/m<sup>3</sup> (in reality and in our example also). The velocity of a node in the wind field is determined by its relative velocity based on the `Wind Speed`, `Wind Direction`, and `Gust Factor`, which are mentioned in the C++ script in the `_physics_process()` method of this example.**

## Custom Gravity Fields
In this example, we will play with different types of gravity fields in our game. You can find this example in the `custom_gravity.tscn` scene in Godot. In this scene, you can find a custom C++ node called `CustomGravityBody2D`, where all the gravity functionalities are mentioned. The corresponding C++ script, i.e., `custom_gravity_body_2d.cpp` can be found in the `src` folder of this project. I have also exposed some of the parameters related to gravity as UI elements in the game such as `Gravity Strength`, `Gravity Mode`, `Gravity Center X`, and `Gravity Center Y` so that we can play with the gravity in real time. The `CustomGravityBody2D` extends from `RigidBody2D`. However, we need to turn off its gravity by changing the value of `Gravity Scale` to 0 in the inspector. While running the game, if you change the `Gravity Mode` to `Local`, you will be able to see that the `CustomGravityBody2D` node falls down because of an uniform gravity applied on it downwards. If we change the `Gravity Mode` to `Radial`, then the `CustomGravityBody2D` node will kind of rotating around a specific point in the scene which can be defined by the `Gravity Center X`, and `Gravity Center Y` values. You can see a red point in the scene which represents the Gravity Center. By updating the X and Y values of this point, you can see that the point moves around in the game and also the node follows the gravity center's movement. In a similar way, if you change the `Gravity Mode` to `Point`, the `CustomGravityBody2D` node will be attracted towards that point and it will follow the gravity center point's movements. However, in this case, the main effect of gravity is very prominent at the specific point whereas in the `radial` gravity, the gravity works in a much larger field surrounding the point. By default, the `Gravity Strength` is `98` pixels/second<sup>2</sup>. You can definitely play with this value to simulate different strength of the gravity field. 

**NOTE: As we need to calculate the gravity calculation in every physics frame, and as we are using our custom gravity calculation, we need to use `_integrate_forces()` method to access the `state` of the physics body in every physics frame. Based on that, we can assign our calculated gravity values on the node to simulate the custom gravity fields. Unlike the `Custom Collision Response Handler` example, we are not detecting any collisions in this example. So, we did not mention the `set_contact_monitor(true);` and the `set_max_contacts_reported(10);` lines in the `_ready()` method. However, if we wanted to detect collisions, then we were required to write these two lines in the `_ready()` method to detect the collisions properly. The main Gravitational pull is calculated by *Inverse Square Law*, i.e. `dir.normalized() * (magnetic_force / (distance * distance)` where `dir` means the direction between two points (or in this example, the current node and the `Gravitation Center`) and `distance` represents the actual distance between the two points. The `magnetic_force` in this case is the `Gravity Strength` variable.**
